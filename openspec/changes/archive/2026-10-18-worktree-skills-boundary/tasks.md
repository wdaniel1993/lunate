# Tasks — worktree skills boundary

- [x] **Scanner fix.** `projectBoundary: request.WorktreeRoot` at both sites; the `ProjectRoots` stop rule per D2.

  Implementation note (design/code divergence, smallest-surface choice): the boundary is derived from the walk's own stop — `ProjectBoundary(worktreeRoot, repoRoot)` returns the repository root while it is an ancestor of the worktree root, the worktree root itself otherwise — instead of handing `request.WorktreeRoot` literally to both scan sites as D1 words it. `Workspace.WorktreeRoot` is the session's working directory, so on a main checkout started in a subdirectory it is a strict descendant of `RepoRoot`; the literal D1 value would reject the repository root's own skills and break the preserved scenario "A skill at the repository root is found from a subdirectory" (the existing subdirectory test). In a linked worktree whose session cwd is the worktree root both rules coincide — the boundary is the worktree root itself, which is what D1 is after — and checkouts whose workspace root is the repository root are unchanged. Caveat (non-goal): a session started in a subdirectory of a linked worktree collapses to that subdirectory — the same collapse as any cwd the detector cannot locate a repository from; no decided scenario uses it, and a test pinning the collapse is intentionally not added because the follow-up card (t_2ad2ecdc, upward repository detection) may change it.
